# v0.1.0-rc.1 Release Checklist

## Objective

Publish the first public norm-spec release candidate from one exact commit,
then prove the GitHub, binary, crates.io, Rust-consumer, and canonical Skill
paths before considering stable `v0.1.0`.

D017 defines the release order, exact-identity rule, partial-publication
handling, and maintainer checkpoints. This checklist records execution evidence;
it does not grant publication authority.

## Baseline

Gate E implementation is complete on `main` at `9e71747`:

- 82 of 82 frozen A1 CLI cases execute without skips;
- 68 Rust test functions and all six conformance pass/failure paths are green;
- Rust 1.97 is the declared MSRV and 1.97.1 is the exact verification toolchain;
- native Linux x64, macOS ARM64/Intel, and Windows x64 archives build, extract,
  execute, and verify on their hosted targets;
- standalone CLI, exact-revision Rust consumer, locked conformance bundle, and
  canonical Skill adoption are proven;
- hosted quality, MSRV, three fixed-platform regression jobs, and four native
  artifact jobs are maintainer-confirmed green for integrated Gate E `main`;
- no local tag exists, and no registry package version is intentionally part of
  this repository's release history yet.

At the D017 checkpoint, explicit `cargo info --registry crates-io` checks found
no public version for `norm-spec-core`, `norm-spec`, or `norm-spec-cli`.
`cargo publish --dry-run -p norm-spec-core --locked` passed. Facade and CLI
dry-runs stopped at their expected absent public upstream package. Package names
remain unreserved until an actual successful upload.

## Phase 1 — Prepare the public packages

- [ ] Add self-contained crate descriptions for core and CLI packages.
- [ ] Include appropriate README and license evidence in every `.crate` file.
- [ ] Add accurate crates.io keywords, categories, and documentation metadata.
- [ ] Restrict publication to crates.io explicitly.
- [ ] Keep `norm-spec` as the recommended public facade; describe core as the
      lower-level semantic engine and CLI as the binary distribution package.
- [ ] Permanently check package metadata and contents in
      `scripts/check-packages.sh`.
- [ ] Confirm every `.crate` contains one exact full source revision in
      `.cargo_vcs_info.json` and no private path, secret, VCS tree, local host
      metadata, contract copy in the facade, or unintended generated content.

## Phase 2 — Prepare the exact RC version

- [ ] Change the workspace version to `0.1.0-rc.1`.
- [ ] Change all internal dependency requirements to `0.1.0-rc.1`.
- [ ] Regenerate and commit `Cargo.lock`.
- [ ] Update exact CLI version fixtures and assertions.
- [ ] Keep format, Rust API, machine API, bundle/report APIs, suite ID, case
      count, and contract digest unchanged unless a separately approved
      compatibility decision says otherwise.
- [ ] Add a fresh `[Unreleased]` section and promote the existing changelog
      content to `[0.1.0-rc.1] - 2026-08-12`.
- [ ] Update README, installation, integration, Rust API, security, status, and
      execution-plan language from development alpha to RC candidate reality.
- [ ] Write release notes that state supported targets, MSRV, checksum and
      signature limits, excluded distribution targets, compatibility identities,
      installation paths, and known pre-stable boundaries.

- [ ] rustdoc with warnings denied.

- [ ] all three workspace package candidates and exact-revision Git consumer.

- [ ] strict self-validation of all `.norm` files.
- [ ] public-history scan.
- [ ] `cargo publish --dry-run -p norm-spec-core --locked` passes.

- [ ] native local archive has version `0.1.0-rc.1`, the exact candidate source

## Phase 4 — Hosted candidate handoff

- [ ] Push the short-lived release-preparation branch.
- [ ] Confirm quality, MSRV, all three fixed-platform regression jobs, and all
      four native artifact jobs for the same exact commit.
- [ ] Confirm all eight uploaded files are named for `0.1.0-rc.1`, have sibling
      checksums, and embed the exact candidate revision.
- [ ] Review Actions logs and artifacts for secrets, private paths, and local
      metadata before changing visibility.
- [ ] Fast-forward the exact candidate to `main`; do not squash, rebase, or add
      a closure commit that changes the release identity.
- [ ] Confirm the same jobs on exact `main`; if `main` SHA differs, discard the
      earlier artifacts and verify again.

## Phase 5 — Maintainer public-repository checkpoint

Stop here until the maintainer explicitly authorizes the visibility change.

- [ ] Confirm organization policy permits public visibility.
- [ ] Review the complete reachable Git history and all retained Actions logs
      and artifacts that will become public.
- [ ] Change `CyanoOrg/norm-spec` from private to public.
- [ ] Confirm canonical URL, default branch, license, README, community profile,
      issue forms, discussions policy, and public Actions rendering.
- [ ] Configure `main` rules: block deletion/force push, require linear history,
      and require the selected unique quality/MSRV/platform/artifact checks.
- [ ] Configure a `v*` tag rule against updates and deletion.
- [ ] Enable private vulnerability reporting and security notifications.
- [ ] Re-run the public-history scan and public unauthenticated clone/read smoke.

## Phase 6 — Maintainer RC publication checkpoint

Stop again until the maintainer explicitly authorizes tag, GitHub Pre-release,
and each crates.io upload.

### Tag and GitHub Pre-release

- [ ] Confirm `main` HEAD equals the fully hosted-green release commit.
- [ ] Create annotated tag `v0.1.0-rc.1` at that exact commit.
- [ ] Push only the intended tag.
- [ ] Create a GitHub Pre-release from the tag and reviewed release notes.
- [ ] Attach exactly four `.tar.gz` archives and four `.sha256` files built by
      the tagged commit; do not rebuild after tagging.
- [ ] Download each public asset, verify its checksum and manifest source
      revision, and run complete native verification where available.

### crates.io serial publication

- [ ] Reconfirm all three exact crate names and the intended owner account.
- [ ] Publish `norm-spec-core = 0.1.0-rc.1`.
- [ ] Wait until `cargo info --registry crates-io norm-spec-core@0.1.0-rc.1`
      resolves; re-run facade dry-run.
- [ ] Publish `norm-spec = 0.1.0-rc.1`.
- [ ] Wait until `cargo info --registry crates-io norm-spec@0.1.0-rc.1`
      resolves; re-run CLI dry-run.
- [ ] Publish `norm-spec-cli = 0.1.0-rc.1`.
- [ ] Never use `--no-verify`; never publish the next package before its exact
      upstream is public.
- [ ] If any upload fails, preserve successful packages, stop, record the exact
      public partial state, and repair forward; do not overwrite versions.

## Phase 7 — Public RC validation

- [ ] Clean-environment
      `cargo install norm-spec-cli --version '=0.1.0-rc.1' --locked` succeeds
      and installs both binaries.
- [ ] Installed `norm compatibility` reports the expected independent product,
      format, Rust API, machine API, and conformance identities.
- [ ] Registry consumer using `norm-spec = '=0.1.0-rc.1'` completes inherited
      collect and packaged validation without a Git or sibling dependency.
- [ ] Public GitHub archive download passes checksum and 82/82 conformance.
- [ ] Canonical Skill installed from the public release archive completes one
      real non-plugin assisted adoption with the released engine.
- [ ] docs.rs renders the facade and core documentation successfully; the CLI
      package page clearly identifies both binaries and external bundle use.
- [ ] Security reporting path and public contribution path are usable.
- [ ] Record every public URL, exact tag/commit, crate version, artifact digest,
      external command result, and known issue in status and release notes.

## Stable promotion criteria

`v0.1.0` remains a separate maintainer decision. Promotion requires:

- every Phase 7 public path green;
- no unresolved format, engine, CLI, package, artifact, installation, or Skill
  blocker found during RC use;
- any necessary fix published as another RC and revalidated;
- no new feature scope in the stable promotion diff;
- a fresh exact stable commit, complete hosted run, four stable-version
  archives, changelog entry, annotated tag, GitHub Release, and serial crate
  publication using the same identity rules.
